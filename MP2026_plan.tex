\section{Assignments}

\subsection{Assignment 1: ``No wheels''}
\textbf{Learning outcome.} Students will be exposed to C programming on real hardware. Students will learn to choose
appropriate variable types, predict and explain overflow and wrap-around, manipulate individual bits with shifts and
masks, use measured user inputs to affect the execution sequence, and produce timed LED behaviour residing on the
hardware and linked to the microcontroller. At this stage, we treat some internal data communication paths, e.g., the
I2C internals, at a high level, leaving deeper dives for later in the course.

\medskip\noindent
\textbf{Provided files:}
\begin{itemize}
\item \texttt{ass1.ioc} - This file maps the connected hardware (i.e. LEDs, pushbuttons) to the Microcontroller lines.
      The provided file maps only the items relevant to the specific assignment.
\item \texttt{io\_board.h} and \texttt{io\_board.c} - These files are part of the C project (STM32CubeIDE) and provide
      ready functions for interacting with the RGB LEDs and the pushbuttons through the communication channel called
      the I2C bus. Students should add within \texttt{main.c}, a call to \texttt{ioBoardInit()} once. This call should
      be in the \texttt{USER CODE BEGIN 2}.
\end{itemize}

\paragraph{Part A: Variable types and range, signed and unsigned, wrap-around.}
\begin{enumerate}[label=A.\arabic*, leftmargin=2.2em]
  \item Increment a \texttt{uint8\_t}, an \texttt{int8\_t}, and a \texttt{uint16\_t} past their limits. Watch them in
        Live Expressions (add a delay so that the changes are slow enough to allow for visual monitoring of the values).
        Print these variables with \texttt{printf} via UART (see tutorial~2) to a terminal application on the PC (e.g., PuTTY) in these formats:
        decimal, hex, and binary. Capture the live output to the terminal in a video you will submit with your report.
        You may choose how to do it, so that the viewer can clearly see the wrap-around (i.e., when a \texttt{uint8\_t}
        is increased beyond $2^8 - 1 = 255$).
        \textbf{Note:} the GNU C library used with STM32CubeIDE supports standard format specifiers such as
        \texttt{\%d}, \texttt{\%u}, \texttt{\%x}, \texttt{\%o}, etc., but there is no standard \texttt{\%b} specifier
        for binary output.
        In your report, describe what happens when a variable exceeds its limit, and explain why.
  \item Explain how to interpret a hex number as a decimal value, and explain the difference between the signed and
        the unsigned cases. Show examples for \texttt{0x7F} (\texttt{uint8\_t} and \texttt{int8\_t}), \texttt{0xF0}
        (\texttt{uint8\_t} and \texttt{int8\_t}) and \texttt{0xFFF6} (\texttt{uint16\_t} and \texttt{int16\_t}).
        In the code, assign each value in its hex form to variables of both types, and print them to PuTTY in hex,
        binary, and decimal. Explain what you see when a negative value is printed in hex.
  \item Integer division and casting. Two students took the MP course. One attended the classes and got 97. The other
        student got 58. Store each grade in an unsigned integer variable, then compute their average: first in a way
        that gives a wrong result because of integer arithmetic, then in a way that gives the correct result. Show both
        in your code and explain the difference in your report.
  % \item A brightness value that wraps around when it is increased past its maximum, then fixed with saturation.
\end{enumerate}

\paragraph{Part B: Bit operations and shifting.}
\begin{enumerate}[label=B.\arabic*, leftmargin=2.2em]
  \item Write the four bit operations as functions (not macros).\\
        The functions will use bitwise operations. Each takes a value and a bit number, and returns the result:
        \texttt{bitSet}, \texttt{bitClear} and \texttt{bitToggle} return the modified value, and \texttt{bitTest}
        returns 0 or 1. For example: \texttt{GPIOA->ODR = bitSet(GPIOA->ODR, 5);}\\
        Use them to affect the Nucleo's green LED (LD2, bit 5 of \texttt{GPIOA->ODR}) directly, without using the HAL
        GPIO functions.\\
        Run this sequence on LD2: wait 1\,s, set the bit (LED on); wait 1\,s, clear it (LED off); then
        three times: wait 1\,s, toggle it. Finally, read the bit with \texttt{bitTest} and show the result on LED 0 of
        the IO board: lit if 1, off if 0.
  \item Moving a single lit LED using bitwise operations. Keep the state of the 8 RGB LEDs in one \texttt{uint8\_t}
        variable, in which bit $n$ represents LED $n$ (1 = lit). Turn on one LED at a time, with 1\,s between steps:
        LED 0, then LED 1, LED 2, and so on. After LED 7 is lit, return to LED 0, and repeat forever. Print the
        variable in binary form at every step.
  \item `Walking' pair of LEDs. Repeat B.2 above, but now with two adjacent LEDs lit: LEDs 0 and 1, then 1 and 2, and so on; after
        LEDs 6 and 7 come LEDs 7 and 0, then 0 and 1 again.
\end{enumerate}
\smallskip\noindent Rules for B.2 and B.3: the variable may change only through bit operations (shifts, OR, AND). Choosing the
pattern with \texttt{if}/\texttt{switch} chains, counters mapped to LEDs, or tables of precomputed patterns is not
accepted. The LEDs are then lit from the variable by testing its bits. In your report, explain how your code moves
the pattern past bit 7 without losing it.
\smallskip
\begin{enumerate}[label=B.\arabic*, leftmargin=2.2em, start=4]
  \item Read the raw button byte with \texttt{readButtonsRaw()}. Using bit operations, convert it into a value in
        which bit $n$ is 1 while button $n$ is held: invert the active-low bits, then clear bits 4 to 7 with a mask.
        Count how many buttons are held (0 to 4) by testing each bit and print the count whenever it changes.
\end{enumerate}

\paragraph{Part C: Input triggering.}
Count the number of times button 0 is pressed, using four versions. In every version, show the count on the 8 RGB
LEDs as an 8-bit binary number (bit $n$ = LED $n$) and print it to the terminal. Update the LEDs and print
\textbf{only when the count changes}: an LED
update or a printed line takes milliseconds, and would slow the loop down. Unless a task says otherwise, the loop has
no delay, so the button is read as fast as possible. In each version, press the button exactly 20 times at a natural
speed and record the count; do it 3 times.
\begin{enumerate}[label=C.\arabic*, leftmargin=2.2em]
  \item Level-based counting: increase the counter on every pass of the main loop while button 0 is held. Also count the loop passes
        per second, and print that number once a second. Explain the count you get.
  \item Edge-based counting: increase the counter only when button 0 changes from released to pressed
        (\texttt{now \& \textasciitilde before}). Do one more round of 20 very light, slow presses. Explain why the
        count is not always 20.
  \item Debounced edge counting: accept a change of the button state only after it has been stable for 20\,ms (use
        \texttt{HAL\_GetTick}).
  \item Missing presses: add \texttt{HAL\_Delay(150)} at the end of the loop of C.3, simulating another process running
        on the microcontroller and not allowing the code to check for button presses. Press the button 20 times, as
        briefly as you can. Repeat with the edge version of C.2 and the same delay.
\end{enumerate}
In your report, put all the results in one table and explain the differences, using the duration of a press and the
time of one loop pass. Explain why presses are lost in C.4, and why the debounced version loses more of them.


\paragraph{Part D: LED blinking and timing.}
\begin{enumerate}[label=D.\arabic*, leftmargin=2.2em]
  \item Write a loop that toggles LD2, prints a status line of about 60 characters to PuTTY with \texttt{printf}, and
        then waits with \texttt{HAL\_Delay(500)}; stop after 200 toggles. Before running it, calculate how long the
        200 toggles will take; then run it and measure. In your report, explain why the total is not exactly
        200 $\times$ 500\,ms (hint: understand the UART).
  \item Blink LD2 (PA5) at a rate set by a global variable that can be changed in the debugger.
  \item Two LEDs blinking at different rates, done twice: first with \texttt{HAL\_Delay}, then non-blocking with
        \texttt{HAL\_GetTick}. Measure and explain the difference.
\end{enumerate}
\paragraph{Part E: Integration and logic.}
Write a program with an \emph{armed} state toggled by button 0 being pressed. The trigger condition is: the system is
armed \textbf{and} the IR sensor (PA7) detects an obstacle.
\begin{itemize}
  \item While the condition holds, all 8 LEDs (white) grow brighter stepwise, from off to full brightness, over
        about 2\,s. When full brightness is reached, the LEDs switch off, and stay off until the condition has become
        false and then true again.
  \item If the condition above is not true while the brightening sequence takes place, the LEDs start dimming, step
        by step, from their current brightness until they become unlit.
\end{itemize}
Set the brightness of all LEDs with \texttt{setRGB(v, v, v)} from \texttt{io\_board.h} ($v$ = 0 to 255). Pace the steps
with \texttt{HAL\_GetTick}, so the inputs are read on every pass of the loop. In your report, give the truth table of
the trigger condition, and draw the behaviour as a state diagram. Creativity bonus applies here.

\paragraph{Part A: Three ways to make a PWM.}
Build the same PWM with the three methods of tutorial~4 (polling, interrupt, hardware), with its symbols $N$, $M$,
$t_\mathrm{step}$ and $f_\mathrm{PWM}$, and find the limits of each. $N$ and $M$ are global variables that you change
from Live Expressions while the program runs.

\smallskip\noindent
\textbf{Hint:} keep two human limits in mind. The eye stops seeing a light flicker above roughly 50 to 100\,Hz, and the
ear hears from about 20\,Hz to 20\,kHz. They decide which PWM frequency is good enough for an LED and for a motor.
\begin{enumerate}[label=A.\arabic*, leftmargin=2.2em]
  \item Method 1, polling, on LD2, with \texttt{HAL\_GetTick} as the step counter ($t_\mathrm{step} = 1$\,ms).
        \emph{This task demonstrates a method that is not good enough, and why.}
        \begin{enumerate}[label=(\alph*)]
          \item With $N = 100$, sweep $M$ from 0 to 100. What $f_\mathrm{PWM}$ do you get, and what do you see?
          \item Use $M = N/2$ and reduce $N$ until the flickering disappears. Note $N$, $f_\mathrm{PWM}$ and the
                number of duty levels that are left. Explain what you see and the trade-off you had to make.
          \item Calculate the $N$ needed for the 17\,kHz PWM that TIM2 uses for the motors, and explain why it cannot
                be done with \texttt{HAL\_GetTick}.
        \end{enumerate}
  \item Method 2, interrupt, with TIM7 at 10\,kHz ($t_\mathrm{step} = 100\,\mu$s, see the configuration section) and
        the same $N$ and $M$ as in A.1.
        \begin{enumerate}[label=(\alph*)]
          \item On LD2, with $N = 100$: what $f_\mathrm{PWM}$ do you get now, and does the LED flicker?
          \item On wheel~1: in the callback, write 0 or 10\,000 to \texttt{TIM2->CCR1} (fully off or fully on). Try
                $N = 100$ and $N = 10$ at 50\,\% duty, and describe the motion and the sound of the wheel.
                \flag{For Bucher, delete before publishing: what is the electrical time constant $L/R$ of the cart's
                motor windings? Can we write that it is about 1\,ms? Then at 100\,Hz (5\,ms on, 5\,ms off) the PWM is not
                fast enough compared with it: the current rises and falls fully in every period, the torque comes in
                pulses, and the motor is very loud.}
          \item Try to make the motors' PWM with method~2: 17\,kHz with $N = 100$. Which TIM7 settings (PSC, ARR) does
                it need, and would it work? Try it, and print the number of main-loop passes per second at 10\,kHz and
                at the new rate.
          \item Measure how long one update of an RGB LED takes over I2C (time 1000 calls of \texttt{setLedChannel}
                with \texttt{HAL\_GetTick}). Explain why method~2 cannot drive the RGB LEDs from the TIM7 callback.
        \end{enumerate}
  \item Method 3, hardware, on wheel~1: TIM2 runs at 17\,kHz with $N = 10\,000$, and \texttt{TIM2->CCR1} sets $M$.
